## 1. What the Project Does

### Problem Statement
Periferia IT Group's administrative team manually transcribes 8–12 supplier-registration forms per month. The data already exists in an internal master repository. The process requires copying it field-by-field into client-provided Excel sheets, PDFs, or web portals, attaching supporting documents, and packaging everything for the legal representative's signature.

### What the Agent Automates
Given a message like `"Procesa el caso ec-corp-andina"`, the agent:

1. **Reads** the client request (`solicitud.json`) and their template (`plantilla-campos.json` or `plantilla-celdas.json`) to extract the list of required fields and supporting documents.
2. **Maps** every field against the master repository (`maestro.json`) using a synonym glossary (`glosario-campos.json`). Each field ends in one of three states: `lleno`, `faltante`, or `requiere_confirmacion`.
3. **Generates** the form in the requested format: `.xlsx` (ExcelJS), `.pdf` (pdf-lib), or a plain-text `valores-portal.md` for portal cases.
4. **Assembles** the signature package: copies available supporting docs to `out/<caso>/paquete/`, writes `checklist.md` (present/absent/expired), writes `borrador-correo.md` (draft email, never with banking data), and evaluates `listo_para_firma`.
5. **Confirms** before any external action. `proveedor_simular_envio` will only write `ENVIO-SIMULADO.md` if called with `confirmado: true`, which the agent only does when the previous user turn explicitly confirmed.

## 3. Domain Logic — Provider Registration

### The Five Tools (contract: always returns `{ ok, data }` or `{ ok: false, error }`, never throws)

```
proveedor_leer_solicitud    args: { caso }
proveedor_mapear_campos     args: { caso, campos[] }
proveedor_generar_formulario args: { caso, mapeo }
proveedor_armar_paquete     args: { caso }
proveedor_simular_envio     args: { caso, confirmado }
```

All defined in `src/tools/proveedor.ts`. Each wraps its logic in a `seguro()` helper (try/catch → `{ ok: false, error }`), then appends a log entry to `out/<caso>/log.jsonl`.

### Field Mapping Algorithm (`src/tools/mapeo.ts`)

1. Look up the field label in `glosario-campos.json` (exact match → confidence 1.0; normalized match without accents/case → confidence 0.9; no match → confidence 0.0).
2. Read the master value via dot-notation (`leerClave()` in `src/domain/maestro.ts`).
3. Apply business rules from `src/domain/reglas.ts`:
   - If confidence = 0 or master value = null → `faltante`.
   - If `clave === "nit"` and `pais !== "CO"` → `requiere_confirmacion` with note "Periferia only has Colombian NIT; client expects RTN/RUC".
   - If confidence < 0.8 → `requiere_confirmacion`.
   - Otherwise → `lleno`.

### Business Rules (`src/domain/reglas.ts`)

| Rule | Implementation |
|---|---|
| RN1: Tax ID by country | `ID_TRIBUTARIO_POR_PAIS` map + `esIdentificadorExtranjero()` |
| RN2: Banking data only if requested | Glosario keys `banco.*` map only; `borrador-correo.md` never includes them (explicit filter in `paquete.ts`) |
| RN3: Expired/absent support blocks signature | `soporteVencido()` + `construirChecklistYCopiar()` accumulates `bloqueos[]` |
| RN4: Human confirmation before external action | `simular_envio.execute()` guards `confirmado !== true` before any I/O |
| RN5: Execution log | `registrarLog()` called in every tool after execution |

## 4. Agent Loop and Tools

### The Turn Loop (`src/agent/loop.ts` → `ejecutarTurno()`)

```
sesion.mensajes.push({ role: "user", content: mensajeUsuario })
for iter in range(MAX_ITERATIONS=25):
    if sesion.tokensUsados > MAX_TOKENS_PER_SESSION:
        return "reached token limit"
    respuesta = await llm.enviar(sesion.mensajes, herramientas)
    sesion.tokensUsados += respuesta.tokens
    if respuesta.toolCalls.length == 0:
        sesion.mensajes.push({ role: "assistant", content })
        return { reply: content, needsConfirmation: pideConfirmacion(content) }
    # else: execute each tool call
    for tc in respuesta.toolCalls:
        validate args with zod schema
        execute tool → resultado (string JSON)
        append to chat history (role: "tool")
        log to out/log.jsonl (global) + out/<caso>/log.jsonl (per-case)
return "reached iteration limit"
```

Key design points:
- **CA1** (iteration cap): `MAX_ITERATIONS=25`, configurable via env.
- **CA2** (no invented values): enforced by prompt + architecture (tools are the only value source).
- **CA3** (human confirmation): `pideConfirmacion()` detects questions containing confirm/send keywords; `needsConfirmation: boolean` returned in API response. The front displays a banner.
- **CA4** (tool call history): every tool call logged globally to `out/log.jsonl` and shown in chat via `toolCalls[]` in the API response.
- **CA5** (error isolation): LLM provider errors are caught and returned as user-readable messages; the session stays alive.

### Session Management (`src/agent/sessions.ts`)

Pure in-memory `Map<string, Sesion>`. Each session holds:
- `mensajes: Mensaje[]` — full conversation history including tool calls.
- `tokensUsados: number` — rolling token count for the cost cap.
- `historialToolCalls: ToolCallEvento[]` — for the `/api/sessions/:id` endpoint.

No persistence; restarts lose sessions (acceptable per PRD §3.2).

## 6. LLM Integration

### Interface (`src/llm/adapter.ts`)

```typescript
interface LLMAdapter {
  readonly provider: string;
  readonly model: string;
  enviar(mensajes: Mensaje[], herramientas: ToolSchema[]): Promise<RespuestaLLM>;
}
```

The loop imports only this interface. Switching providers is a single env var change.

### Mock Adapter (`src/llm/mock.ts`)

A deterministic state machine that implements the correct agent flow without any API call:
1. Detect the `caso` from the conversation.
2. Detect if the user's last message confirms a send.
3. Track which tools have already been called (by scanning `role: "tool"` messages).
4. Return the next tool call in the sequence, or compose a final summary with a confirmation question.

This makes `npm run demo` and the chat fully functional with no API key.

### OpenAI Adapter (`src/llm/openai.ts`)

Chat Completions endpoint with `tool_choice: "auto"` and `temperature: 0`. Maps the internal `Mensaje[]` format to OpenAI's message schema (handles `role: "tool"` messages correctly). Reads `OPENAI_API_KEY` / `OPENAI_MODEL` from env.

### Anthropic Adapter (`src/llm/anthropic.ts`)

Messages API with tool use. Extracts the system message separately (Anthropic requires it as a top-level field). Maps `role: "tool"` messages to `role: "user"` content with `type: "tool_result"`. Reads `ANTHROPIC_API_KEY` / `ANTHROPIC_MODEL` from env.

### Security

Neither adapter logs nor exposes the API key. `/api/health` returns only `{ ok, provider, model }`. Keys are never in `web/` JS or HTTP responses.

## 8. Conclusions and Quality Assessment

### Strengths

1. **Architectural discipline**: The behavior/knowledge/execution split is cleanly maintained. `reglas.ts` has zero I/O; `types.ts` has zero dependencies; tools never leak server concerns.

2. **Deterministic demo**: The mock adapter is a first-class implementation, not a stub. It exercises the full tool pipeline including confirmation-gate semantics. `demo.ts` cleans `out/` before running, guaranteeing reproducible output.

3. **Error safety**: The `seguro()` wrapper in every tool, and the try/catch in `ejecutarTurno()` for LLM failures, means the agent never crashes. Every tool result is typed `ToolResult<T>`.

4. **Tool contract fidelity**: Registry auto-builds tool names as `<file>_<export>` exactly as the PRD specifies. Args are zod-validated before execution; validation errors go back to the model as tool results (not thrown).

5. **Cost controls**: Both `MAX_ITERATIONS` and `MAX_TOKENS_PER_SESSION` are configurable via env. A user cannot exhaust an API key without a server restart.

6. **No invented data**: The field-mapping logic in `mapeo.ts` has only three outcomes. There is no fallback that guesses or hallucinates a value. If a key is in the glosario but absent from the master, the state is `faltante`, not a guess.

7. **Bonus module (`modulo/`)**: The module re-exports (not copies) the same tools from `src/tools/proveedor.ts`. `modulo/agent.md` is a proper Kiro/agent-platform frontmatter file with `permission: { edit: deny, bash: deny }`. The SKILL.md is clean and condensed.

### Minor Observations / Potential Improvements

1. **`pideConfirmacion()` heuristic** (`src/agent/loop.ts:L56`): Uses a regex on the assistant's text content to detect if a confirmation question was asked. This works well with the mock adapter (which produces deterministic output) but may produce false positives/negatives with real LLMs that phrase confirmations differently. A more robust approach would be to have the agent emit a structured signal (a special tool call or a JSON field) rather than relying on text pattern matching. This is a low-risk issue for the demo but worth noting for production.

2. **Missing `.gitignore` entry for `out/`**: The PRD says `out/` should not be committed. The `.gitignore` should confirm this. (Not verified by file read, but `out/` is dynamically generated by `demo.ts` which deletes it first — low risk.)

3. **`plantilla-campos.json` missing for `pa-logistica-istmo`**: The portal case has no template file, which is intentional per the PRD (portal has no attached template). The tool handles this correctly by leaving `campos` empty and calling `generarPortal()`. This is correct behavior but means the portal values-portal.md will have no rows — the SOLUCION.md acknowledges this.

4. **`generarXlsx()` does not write etiqueta cells** (`src/tools/generadores.ts:L24-35`): The template defines `celda_etiqueta` (the label cell) alongside `celda_valor` (the value cell), but the generator only writes values. The label cells are left empty. The PRD says "escribiendo cada etiqueta y su valor exactamente en la hoja y celda indicadas" — this is a small gap where labels could be written alongside values.

5. **No test suite**: There are no automated tests (no `*.test.ts`, no test framework in `package.json`). The `demo.ts` serves as an integration test, but unit tests for `mapeo.ts` and `reglas.ts` (which are pure functions) would be easy to add and would strengthen confidence in the domain logic.

6. **Deployment not done**: `README.md` states "Pendiente de desplegar." The PRD grants −10 points for this. The application is structureless from a deployment perspective (single Node process, no state files, no database), so Railway/Render/Fly.io deployment would be straightforward.
